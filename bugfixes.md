# Project Heal — Bug Fix & Issue Tracker

> **Purpose**: Track every bug found, how it was fixed, why that fix was chosen, and any open issues.
> **Rule**: Every new bug gets appended. Never delete entries — mark as `✅ Fixed` or `🔄 Open`.

---

## How to Use This File

When a bug is found:
1. Add it under the appropriate category
2. Include: **Date Found**, **Severity** (P0-critical/P1-high/P2-medium/P3-low), **Description**, **Root Cause**, **Fix**, **Why This Fix**, **Commit**
3. When fixed, mark `✅ Fixed` and add the fix date

When a new issue is discovered but not yet fixed:
1. Add under "Open Issues" with **Proposed Solution**

### BUG-005 · K8s executor pod template labels contained `pod-template-hash`
- **Date Found**: ~14 Oct 2026
- **Severity**: P1 (rollback would create orphan ReplicaSets)
- **Description**: When applying a rollback, the pod-template-hash label from the old ReplicaSet was included in the patch, causing Kubernetes to create a new ReplicaSet instead of matching the existing one.
- **Root Cause**: `sanitize_for_serialization()` preserved all labels including `pod-template-hash` which is auto-managed by K8s.
- **Fix**: Strip `pod-template-hash` from both rollback and undo template metadata before patching.
- **Why This Fix**: `pod-template-hash` is auto-generated by K8s controller. Including it in a patch creates a mismatch and new ReplicaSet. Stripping it lets K8s regenerate the correct hash.
- **Commit**: `ff9c6e8 fix(executor): sanitize pod template labels and add live cluster diagnostics to CI`
- **Status**: ✅ Fixed

### BUG-007 · Unmasked telemetry events accepted without server-side verification
- **Date Found**: ~14 Oct 2026 (discovered during PRD D-14 implementation)
- **Severity**: P0 (security — data perimeter violation)
- **Description**: The brain relied solely on a client-set `masking_applied` boolean flag. No server-side content inspection.
- **Root Cause**: Original design treated the masking flag as authoritative. PRD D-14 identified this as advisory only.
- **Fix**: Added `ContentScanner` service that runs regex + Shannon entropy detection on every inbound payload. Fails closed on findings.
- **Why This Fix**: Defense in depth. The client flag could be wrong or spoofed. Server-side scan is the actual security boundary.
- **Commit**: Part of `5ac9b3b feat(brain): k8s informers, zero-fabrication evidence gate, sqlite approvals, and negative test suite`
- **Status**: ✅ Fixed

### BUG-009 · Async Slack approval not responding within 3 seconds
- **Date Found**: ~16 Oct 2026
- **Severity**: P1 (Slack times out after 3s → user sees error)
- **Description**: Slack interactive endpoints must acknowledge within 3 seconds. The approval endpoint was waiting for rollback execution before responding.
- **Root Cause**: Synchronous execution of rollback within the HTTP handler.
- **Fix**: Approval endpoint validates HMAC and immediately returns HTTP 200 (`execution_status: "in_progress"`) in <50ms. Rollback runs as `asyncio.create_task`, persists state in SQLite, and updates Slack via `response_url`.
- **Why This Fix**: Slack will show an error to the user if the endpoint doesn't respond within 3s. Background task pattern decouples response time from action duration.
- **Commit**: Part of `1da7bf5 feat(core): production readiness, background collector lifespan, and real cluster test gaps`
- **Verified**: Test with 5s delayed mock executor confirms sub-50ms HTTP response.
- **Status**: ✅ Fixed

### BUG-011 · No crash recovery for in-progress approvals
- **Date Found**: ~17 Oct 2026
- **Severity**: P1 (data integrity — orphaned approvals after crash)
- **Description**: If the agent crashed while executing a rollback (between approval and verification), the approval stayed in `in_progress` state forever.
- **Root Cause**: No startup reconciliation logic.
- **Fix**: On startup, query all `in_progress` approvals, reconcile with live cluster state, mark `needs_human_review`, create audit entry, alert Slack.
- **Why This Fix**: Crash recovery must be safe — we can't assume what happened, so we flag for human review rather than auto-completing or auto-aborting.
- **Commit**: `8eb92cd feat(hardening): background watches, crash recovery, workload lock and cooldown, response_url validation`
- **Status**: ✅ Fixed

### BUG-012 · No workload lock or cooldown enforcement
- **Date Found**: ~17 Oct 2026
- **Severity**: P1 (safety — concurrent rollbacks on same workload)
- **Description**: Multiple approvals on the same workload could execute simultaneously or within the cooldown period.
- **Root Cause**: No locking or rate-limiting mechanism per workload.
- **Fix**: Added workload lock (HTTP 409 on concurrent execution) and cooldown timer (configurable, default 30 min) per PRD F-09/F-10.
- **Commit**: `8eb92cd`
- **Status**: ✅ Fixed

### BUG-013 · Slack `response_url` vulnerable to SSRF
- **Date Found**: ~17 Oct 2026
- **Severity**: P0 (security — SSRF via crafted response_url)
- **Description**: The `response_url` from Slack interactive payloads was not validated. A crafted payload could redirect approval callbacks to an attacker-controlled server.
- **Root Cause**: No host validation on `response_url`.
- **Fix**: Strictly validate `response_url` host against `hooks.slack.com` (HTTPS only, no userinfo, no custom ports).
- **Why This Fix**: SSRF mitigation. Only legitimate Slack webhook hosts should receive our callback data.
- **Commit**: `8eb92cd`
- **Status**: ✅ Fixed

### BUG-014 · Non-atomic workload lock allowed race condition during concurrent approvals
- **Date Found**: 18 Oct 2026
- **Severity**: P1 (safety / concurrency race)
- **Description**: The workload lock checked active execution status and updated `in_progress` across separate transactions, permitting concurrent approvals on the same workload to race and potentially run parallel rollbacks.
- **Root Cause**: Missing atomic acquisition transaction and missing database-level unique constraint on active workload locks.
- **Fix**: Added SQLite UNIQUE partial index (`idx_active_workload_lock ON approvals (namespace, target_service) WHERE execution_status = 'in_progress' AND target_service != ''`), atomic `acquire_workload_lock` transaction, and a true concurrent race test using `asyncio.gather`.
- **Why This Fix**: Guarantee atomicity at both the application thread level (mutex) and the database engine level (unique constraint + transaction).
- **Status**: ✅ Fixed

### BUG-015 · Slack `response_url` validation lacked prefix pattern required for CodeQL SSRF recognition
- **Date Found**: 18 Oct 2026
- **Severity**: P1 (security / CodeQL compliance)
- **Description**: URL validation relied solely on `urlsplit` without checking `startswith("https://hooks.slack.com/")` in the same code path, risking CodeQL SSRF false-positive alerts.
- **Root Cause**: Missing explicit prefix check expected by static analysis / CodeQL rules.
- **Fix**: Enforced both `startswith("https://hooks.slack.com/")` and strict parsed hostname/netloc validation in the same path; confirmed tests for `hooks.slack.com.evil.com`, `evil.com/hooks.slack.com`, `hooks.slack.com@evil.com`, and `http://`.
- **Why This Fix**: Standard defense-in-depth and static analysis alignment.
- **Status**: ✅ Fixed
